**Deterministic scan**: 24 findings from `impeccable detect` (10× font-size, 9× color, 3× radius, 2× side-tab) — flat vs. last run's 24. ## Overall Impression

The fixes from the last critique are real and mostly clean — the focus-ring bug in particular was root-caused and removed, not patched, and both assessments independently confirmed this by inspecting actual compiled CSS. But expanding scope to consumer sites (as requested) surfaced something the showcase-only critiques couldn't see: the product's entire reason to exist — "a fix or improvement lands once and propagates, rather than being re-implemented per site" — is being defeated in practice. `comphot`'s 16 parameter sliders and the lab site's pagination buttons hand-roll primitives the library already ships, and the lab site's hand-rolled button reintroduces a broken focus-outline override — the exact same bug class that was just fixed upstream, one layer up, un-caught. Score held flat at 30/40: real progress on the showcase, offset by real debt found once you looked past it.

## Priority Issues

**[P1] Component counts are still wrong — only internally reconciled, not accurate.**
- **Why it matters**: `src/routes/components/+page.svelte` no longer hardcodes "96," but the per-category counts it sums (22+10+11+…) still total 91, hand-typed and untouched by the fix. Actual `src/lib` file count is 110; the `index.ts` export count came back as 110 from one assessment's grep and 107 from the other's — a different grep pattern matching different things. That disagreement is itself the point: nothing in this repo can currently answer "how many components does this library have" with one authoritative number, and this is the entry page a new developer treats as documentation.
- **Fix**: Derive `count` per category from an actual import map or `index.ts` at render time, and add a test asserting the sum equals the real export count so this can't silently drift again.
- **Suggested command**: /impeccable harden

**[P1] Consumer sites hand-roll primitives the library already ships, defeating "one shared surface."**
- **Why it matters**: `pages/comphot`'s `plant-memory` and `experiments` pages contain 16 raw `<input type="range">` elements with no `accent-color` — rendering the browser's default blue instead of RWTH petrol — instead of the library's own `Slider`/`Slider2`, which already sets `accent-color: var(--color-primary)`. This is comphot's most interactive content, on a public, i18n, WCAG-AA-committed education site, and it carries none of the library's brand or accessibility treatment. Separately, the lab site's `News.svelte`/`Tutorials.svelte` hand-roll pagination buttons that reimplement `Button`'s hover trick and ship an invalid `outline: 1px` rule — dropped by the CSS parser, so the button silently falls back to the browser's default focus ring instead of the petrol `:focus-visible` ring every real `Button` on the same page now gets correctly. The bug class just fixed upstream (P0, last run) is already back, one layer up, uncaught.
- **Fix**: Migrate comphot's range inputs to `Slider`/`Slider2`; migrate the lab site's pagination buttons to `ButtonIcon` (which `mxl-web` already uses correctly in 8 files for this exact need).
- **Suggested command**: /impeccable audit (grep all pages/* for type="range" and hand-rolled buttons with custom hover CSS), then /impeccable polish on the two flagged sites.

**[P2] `InfoBox`'s side-tab border pattern is undocumented for the third straight run, and its CSS is redundant.**
- **Why it matters**: `InfoBox.svelte:86,88` layers three border declarations (`border-left: 4px solid`, then a `border: 1px` shorthand that overwrites it, then a second `border-left-width: 4px` to restore it) to produce one effective style — a real quality smell independent of the detector call. DESIGN.md documents Card's top-border as a named pattern but has never done the same for InfoBox's side-tab, so the detector keeps flagging an intentional-looking pattern as unreviewed.
- **Fix**: Collapse the CSS to one declaration; add a named rule to DESIGN.md documenting InfoBox's side-tab as intentional.
- **Suggested command**: /impeccable document

**[P2] The new input `error` state has real accessibility gaps.**
- **Why it matters**: `InputCheckbox.svelte` sets `border-color: var(--color-danger)` on a completely unstyled native checkbox with no `appearance: none` — native checkbox border rendering isn't reliably honored across engines, repeating the exact silent-failure shape as the just-fixed `InputNumber` class bug. Neither the input error message nor `InfoBox`'s `error` variant (`role="note"`) uses `aria-live`/`role="alert"`, so a screen-reader user who doesn't refocus the field won't be proactively told an error appeared.
- **Fix**: Verify/fix checkbox error rendering across browsers; add `role="alert"` or `aria-live="assertive"` to both error surfaces.
- **Suggested command**: /impeccable harden

**[P3] The new `error` prop has zero showcase coverage.**
- **Why it matters**: None of the seven sections on `src/routes/components/inputs/+page.svelte` demo `error` on any input. Per this project's own showcase-as-documentation principle, a brand-new, accessibility-relevant prop shipped with no discoverable example is effectively undocumented for anyone who doesn't read source.
- **Fix**: Add one error-state example per input component to the existing showcase sections.
- **Suggested command**: /impeccable document
